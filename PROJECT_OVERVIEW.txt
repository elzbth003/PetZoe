================================================================================
 PETZOE — PROJECT OVERVIEW
 Pet Healthcare, Adoption & Marketplace Platform
================================================================================

TECH STACK
--------------------------------------------------------------------------------
Frontend : React 19 + Vite + Tailwind CSS v4, React Router v7, React Hook Form,
           Zod, Framer Motion, Recharts, Axios, @react-oauth/google
Backend  : Spring Boot (Java), Spring Security + JWT, Spring Data JPA
Database : PostgreSQL
Auth     : Email/password (BCrypt + JWT) and Google Sign-In (ID token verified
           server-side)

USER ROLES
--------------------------------------------------------------------------------
The whole platform is built around five roles, stored as a free-text "role"
field on the User table and enforced both by JWT-derived Spring Security
authorities and by per-route guards on the frontend:

  1. Pet Owner          - the default role for anyone who registers normally
                           or signs in with Google for the first time
  2. Veterinarian        - must be verified by an Admin before doing vet work
  3. Shelter Manager     - runs one Shelter; must be verified before intake
  4. Marketplace Seller  - must be verified before products can be approved
  5. Admin               - reviews and approves/rejects everyone else

================================================================================
 2. BACKEND MODULE WORKFLOWS
================================================================================

2.1  Auth  (AuthController "/api/auth" -> AuthService)
--------------------------------------------------------------------------------
  POST /register          Creates a User (password BCrypt-hashed). If role is
                           "Marketplace Seller", a PENDING VerificationRequest
                           is opened immediately and admins are notified;
                           otherwise the user gets a welcome notification.
  POST /login              Spring AuthenticationManager verifies credentials,
                           JwtService issues a JWT.
  POST /google             Verifies the Google ID token (GoogleIdTokenVerifier;
                           audience check is skipped only if no client ID is
                           configured — dev mode). Links to an existing user
                           by googleId or email, or auto-registers a new
                           "Pet Owner".
  POST /forgot-password    Confirms the email exists; the reset email itself
                           is currently simulated, not actually sent.

2.2  User & Admin management
--------------------------------------------------------------------------------
  UserController        GET/PUT /api/users/me, password change, delete own
                         account.
  AdminUserController   GET /api/admin/users (list all), PUT
                         /api/admin/users/{id}/status?enabled= (enable/
                         disable any account).
  AdminController       GET /api/admin/dashboard/stats (pending counts),
                         /activity (last 50 audit-log rows), /analytics
                         (30-day registration trend, role distribution,
                         verification-status distribution).

2.3  Marketplace — Products  (product lifecycle / state machine)
--------------------------------------------------------------------------------
  ProductController        Public browsing only — list/detail/search/by-
                            category/featured/new-arrivals; only ever returns
                            APPROVED products.
  VendorProductController  Seller-owned CRUD on their own products.
  AdminProductController   Admin approve/reject queue.

  Status flow:  DRAFT -> (seller submits, requires seller's own account
                already APPROVED) -> PENDING_REVIEW
                PENDING_REVIEW -> admin approve -> APPROVED (seller notified)
                PENDING_REVIEW -> admin reject (reason required) -> REJECTED
                                  (seller notified, can edit & resubmit)
                Editing a live APPROVED/OUT_OF_STOCK product resets it back
                to DRAFT (must be re-reviewed).
                Deleting is blocked once a product is APPROVED.
                Stock hits 0        -> auto flips to OUT_OF_STOCK
                Restocked from 0    -> auto flips back to APPROVED

2.4  Marketplace — Cart / Wishlist / Orders / Reviews / Categories
--------------------------------------------------------------------------------
  CartController        Get/add/update-quantity/remove/clear (Pet Owner).
  WishlistController     Get/add/remove/move-to-cart (Pet Owner).
  OrderController/       placeOrder: reads the cart, row-locks each Product
   OrderService          (findByIdForUpdate) to prevent overselling under
                         concurrent checkout, validates stock, snapshots the
                         price paid into OrderItem.priceAtPurchase, decrements
                         stock, creates the Order ("Pending"), clears the
                         cart. Admin can list all orders / update status.
  ReviewController       Public GET reviews per product; Pet Owner can post
                         exactly one review per product (DB-enforced unique
                         constraint).
  CategoryController     Public GET; CRUD endpoints exist for admin use.

2.5  Adoption — Public browsing & applications
--------------------------------------------------------------------------------
  PublicAdoptionController   Unauthenticated search/browse of adoptable
                              animals and animal detail.
  AdoptionApplicationController / AdoptionApplicationService
    saveDraft   Editable only while DRAFT or ADDITIONAL_INFORMATION_REQUIRED;
                requires an existing AdopterProfile.
    submit      Animal must be READY_FOR_ADOPTION and its shelter APPROVED;
                adopter profile must be complete (address, housing type,
                living arrangement, can-provide-food/housing, reason for
                adoption). DRAFT/ADDITIONAL_INFORMATION_REQUIRED -> SUBMITTED,
                shelter manager notified.
    withdraw    Allowed from DRAFT, SUBMITTED, UNDER_REVIEW,
                ADDITIONAL_INFORMATION_REQUIRED, HOUSE_CHECK_PENDING,
                HOUSE_CHECK_COMPLETED, SHELTER_REVIEW -> WITHDRAWN.
  ShelterApplicationController  Currently read-only on the shelter side —
                              shelters can view applications for their
                              animals; the approve/reject/house-check
                              decision workflow is a planned later phase.
  AdopterProfileController     Get/update the reusable one-per-user adopter
                              profile.

2.6  Adoption — Shelter-side listing & animal management
--------------------------------------------------------------------------------
  ShelterController      Get/update own Shelter profile, add/remove
                         documents, submitForVerification (validates all
                         required fields + at least one document) -> Shelter
                         & manager User both go to PENDING, admins notified.
  AnimalController /     createIntake (only if shelter is APPROVED) creates
   AnimalService         an Animal (IN_SHELTER_CARE) + AnimalIntake row, and
                         auto-generates an animalCode like "PZA-000123".
                         recordInitialAssessment fills the shelter-observed
                         health fields. uploadDocument attaches a
                         MedicalDocument. updateAnimalStatus is restricted to
                         shelter-settable statuses only (IN_SHELTER_CARE,
                         UNDER_MEDICAL_CARE, MEDICAL_REVIEW,
                         AWAITING_DOCUMENTS, ON_HOLD, WITHDRAWN) — a shelter
                         can never directly mark an animal adopted.
  AdoptionListingService  Shelter drafts listing content (personality,
                         description, adoption fee, size, special-care
                         notes) while the animal is in an editable status.
                         submitForAdoptionReview requires: initial assessment
                         done, at least one vet MedicalRecord exists,
                         personality + description filled, and the animal
                         is NOT currently UNDER_MEDICAL_CARE/MEDICAL_REVIEW.
                         -> Animal: ADOPTION_REVIEW, Listing: PENDING, all
                         admins notified.
  AdminAdoptionListingService  approve (listing PENDING/UNDER_REVIEW ->
                         APPROVED, animal -> READY_FOR_ADOPTION, now publicly
                         visible), reject (-> REJECTED, animal -> ON_HOLD,
                         reason required), requestChanges (-> CHANGES_
                         REQUIRED, animal -> AWAITING_DOCUMENTS, reason
                         required).
  AdminShelterService     approve / reject / requestChanges / suspend — each
                         syncs both the Shelter's and the manager User's
                         verificationStatus together, updates the linked
                         VerificationRequest, and notifies the manager.

2.7  Veterinary — verification & clinical care
--------------------------------------------------------------------------------
  VerificationController   Generic self-submission endpoint used by roles
                            like sellers (creates/updates a
                            VerificationRequest, sets User.verificationStatus
                            = PENDING).
  AdminVeterinarianService  A richer, vet-specific verification pipeline
   (separate from the generic one):
      markUnderReview     PENDING/RESUBMISSION_REQUIRED -> UNDER_REVIEW
      approveVeterinarian Only from UNDER_REVIEW, AND only if every uploaded
                          VerificationDocument is individually APPROVED
                          (rule-engine gate; at least one document required)
      rejectVeterinarian /
      requestResubmission Reason required for both
      reviewDocument      Approve/reject an individual document with reason
      Every transition writes a VerificationHistory row + an AuditLog row
      and notifies the vet. User.verificationStatus is the single source of
      truth for the vet's overall status.
  VetAnimalController /     Vet's worklist of shelter animals: add
   MedicalRecordService     MedicalRecord / Vaccination / PreventiveCareRecord
                            entries, upload/verify MedicalDocuments, move an
                            animal between medical-care statuses.
  AppointmentController /   Pet Owner books an appointment for their own pet
   AppointmentService       with a Veterinarian user (status "UPCOMING"), can
                            cancel their own appointments; the vet views
                            their appointments and marks them
                            COMPLETED/CANCELLED (owner is notified either way).
  VetController /           Public vet directory search; Pet Owner CRUD on
   PetController            their own pet profiles.

2.8  Notifications
--------------------------------------------------------------------------------
  NotificationController / NotificationService — list, mark-as-read, delete,
  unread-count. Used everywhere across the backend (registration,
  verification transitions, product approval/rejection, order events,
  appointment completion/cancellation, every step of the adoption workflow)
  via a single notificationService.createNotification(user, title, message,
  type, [reason], [referenceId]) call.

2.9  Admin dashboard stats / analytics / audit
--------------------------------------------------------------------------------
  AdminController -> AdminService / AdminAnalyticsService:
    dashboard/stats     pendingVets, pendingShelters, pendingSellers,
                        pendingProducts, totalUsers, totalPetOwners,
                        verifiedVets, activeAdoptionPets (drives the admin
                        sidebar badges and dashboard metric cards)
    dashboard/activity  last 50 AuditLog rows (admin actions only)
    dashboard/analytics 30-day daily user-registration counts, role
                        distribution, verification-status distribution
                        (all computed via grouped SQL queries)

  type  free string, not null (APPOINTMENT / VACCINATION / PROFILE /
    SYSTEM / PRODUCT_APPROVED / VERIFICATION / ACCOUNT_APPROVED /
    ACCOUNT_REJECTED, etc.)
  reason (2000); referenceId; isRead (default false); createdAt

================================================================================
 4. HOW A FEW END-TO-END FLOWS TIE TOGETHER
================================================================================

Marketplace Seller onboarding:
  Register as "Marketplace Seller"
    -> VerificationRequest opened automatically (PENDING), admins notified
    -> Admin reviews under Seller Verification (generic VerificationQueue)
    -> Approved: seller's User.verificationStatus = APPROVED
    -> Seller can now create Products (start in DRAFT) and submit them
    -> Admin reviews under Product Moderation -> APPROVED/REJECTED
    -> Approved products appear publicly on the Marketplace

Shelter -> Adoption pipeline:
  Shelter Manager registers, fills Shelter Profile, submits for verification
    -> Admin approves (Shelter + manager both -> APPROVED)
    -> Shelter can now record Animal intakes (IN_SHELTER_CARE)
    -> Shelter records initial assessment; a Veterinarian adds at least one
       MedicalRecord for the animal
    -> Shelter drafts an AdoptionListing and submits for review
       (animal -> ADOPTION_REVIEW, listing -> PENDING)
    -> Admin approves (animal -> READY_FOR_ADOPTION, listing -> APPROVED)
    -> Animal now appears publicly under /adopt
    -> A Pet Owner completes their AdopterProfile and submits an
       AdoptionApplication (-> SUBMITTED), shelter manager notified
    -> (Shelter-side decisioning of the application is a planned next phase)

Veterinarian verification:
  Register as "Veterinarian", upload VerificationDocuments
    -> Admin marks UNDER_REVIEW
    -> Admin (or the vet) resolves each document individually
       (approve/reject)
    -> Admin can only approve the vet once every document is APPROVED
    -> Approved vet can now be booked for Appointments and can manage
       shelter animals' medical records

Order checkout:
  Pet Owner adds Products to cart -> checkout
    -> Each product row is locked and re-validated for stock
    -> Order created ("Pending"), OrderItems snapshot the price paid,
       stock decremented, cart cleared
